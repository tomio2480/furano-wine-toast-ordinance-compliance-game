# 🧱 技術構成と複雑度の抑え方

## 📝 要約

ゲームの技術構成を決めた経緯を記録する．
利用者は，動作の軽さに加え，`cccc` で測る複雑度が上がりにくい構造を求めた．
素の TypeScript と Vite を使い，Canvas 2D と HTML/CSS を併用する構成を採った．
分岐を表と CSS へ逃がす設計と，CI での上限 8 の検査で複雑度を抑える．

## 🧭 背景

- 要件書は TypeScript，Vite，Canvas 2D，Vitest，Playwright を案として挙げていた
- 利用者は，軽さに加えて `cccc` で測る複雑度が上がりにくい構成を求めた
- `cccc` は `moznion/cccc` の CLI である．Cognitive と Cyclomatic を関数ごとに測る

## 📏 cccc の採点規則

README（v1.10.0）で確かめた規則のうち，構成の選択に効くものを挙げる．

- Cyclomatic は関数ごとに 1 から始まり，`if`・三項・ループ・`case`・`catch` で加点する
- `&&`・`||`・`??` と，optional chaining の各段も Cyclomatic に加点する
- Cognitive は `if`・三項・`switch`・ループ・`catch` に入れ子の深さを足す
- 関数の境界で入れ子は 0 に戻る．入れ子の関数は親と別に採点する
- 閾値の判定は関数だけが対象で，モジュール直下のコードは判定しない

このため複雑度は，構成の選び方より，分岐をどこへ置くかで決まる．

## ✅ 判断

- 素の TypeScript と Vite を使い，UI フレームワークは入れない
- プレイ領域は Canvas 2D 1 枚で描く．描画の手続きは分岐をほとんど含まない
- メニューと HUD は HTML と CSS で組む．読み上げとキー操作はブラウザの標準機能に任せる
- 画面や乾杯状態の見た目は，ルート要素の data 属性と CSS で切り替える
- 飲み物・難易度・画面遷移・称号・共有先は表として持ち，参照で引く
- 繰り返しは配列メソッドへ寄せ，判定は名前の付いた小さな関数へ切り出す
- 値の不在は空配列などで表し，`?.` と `??` を減らす
- CI で `cccc` v1.10.0 を回し，どちらかの指標が 8 を超えたら落とす
- バイナリは版を固定し，SHA-256 を workflow へ直書きして照合する
- 手元では `npm run complexity` で同じ上限を確かめる

## 🔀 代替案と棄却理由

- Preact でメニューを書く: TSX 内の条件式が描画関数の複雑度に加わり，依存も増える
- SVG と DOM で描く: 参加者ごとの要素の生成と破棄に分岐が増え，演出の多い場面で重くなる
- 汎用のゲームエンジン: 本作の規模では機能の大半を使わず，転送量の目安を圧迫する
- Svelte や Vue の単一ファイル部品: `cccc` は拡張子で振り分けるため，`.svelte` と `.vue` を測れない
- `moznion/cccc-action`: 既定で最新版を取得し，期待するハッシュを渡す入力がない

単一ファイル部品は，測れない場所へ複雑度を移すだけになる．このため採らない．
